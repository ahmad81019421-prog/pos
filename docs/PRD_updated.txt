POS PROJECT CONTEXT

1. Project Overview

Build a professional, offline-first Windows desktop POS and store management application for small and medium-sized local shops that primarily sell:

- Chicken / poultry products
- Cheese
- Dairy products
- Fish
- Packaged food products
- Other products that the shop owner may add manually

The application is intended for shops that currently rely heavily on paper notebooks and manual calculations.

The product must therefore prioritize:

1. Simplicity
2. Speed
3. Reliability
4. Very clear UX
5. Minimal data entry
6. Attractive professional appearance
7. Offline operation
8. Accurate financial calculations
9. Easy installation and maintenance
10. No unnecessary enterprise complexity

This is NOT an ERP system and NOT a SaaS product.

The software is sold as a one-time purchase and runs entirely on the customer's Windows computer.

---

2. Core Business Model

The application is:

- A Windows desktop application
- Installed on one computer per shop
- Completely local
- No cloud database
- No remote server
- No online account
- No internet dependency
- No subscription
- No multi-tenant architecture
- No online synchronization

The database is SQLite and resides locally on the customer's computer.

The application must continue functioning normally if:

- Internet is unavailable
- Wi-Fi is unavailable
- The computer has never been connected to the internet

All normal POS operations must work offline.

Use:

      v

12. Two Weight-Selling Workflows

The system must support both of the following workflows.

Workflow A — Weight × Unit Price

Example:

Product:
Chicken Breast

Price:
$4.50 / KG

Weight:
1.350 KG

Calculated Total:
$6.075

The system calculates the total automatically.

The application must apply the configured currency precision/rounding rules.

---

Workflow B — Enter Final Price Directly

Some shops use a digital scale that calculates the final selling price.

The shop owner may already be accustomed to seeing something like:

Weight = 1.350 KG
Final Price = $6.08

In this situation, the cashier must be able to enter the final price directly.

The system must NOT force the cashier to repeat a calculation that the scale already performed.

The sale record should preserve:

- Product
- Weight
- Unit
- Final price
- Currency

This workflow is critical.

16. Exchange Rate

The application maintains a current USD/LBP exchange rate.

Example:

1 USD = 89,500 LBP

The exchange rate can be changed by the shop owner.

However:

IMPORTANT:

The exchange rate must NOT be displayed as an easily editable field on the main POS screen.

It should be located inside Settings.

The goal is to reduce accidental or unauthorized manipulation.

Changing the exchange rate affects new calculations only.

Historical transactions must retain the exchange rate used at the time of the transaction.

---

17. LBP Rounding

Lebanese Pound cash calculations must support rounding to the nearest 5,000 LBP.

Example:

87,300 LBP

becomes:

90,000 LBP

The rounding behavior must be implemented consistently throughout:

- Product conversion
- Payment
- Change
- Mixed currency calculations

Do not use floating-point arithmetic for financial storage.

Use integer-based minor units / precise decimal arithmetic where appropriate.

---

18. Financial Precision

Do NOT use JavaScript floating-point arithmetic directly for monetary accounting.

Money calculations must be deterministic.

Recommended approach:

- Store LBP as integer amounts.
- Store USD using an appropriate fixed precision representation.
- Use a decimal arithmetic library if needed.
- Round only at clearly defined boundaries.

All financial calculations must have automated tests.

45. Backup

Because the application uses local SQLite, backup is critical.

Implement automatic backups.

Recommended behavior:

- Automatically create a backup at least daily.
- Keep multiple recent backups.
- Avoid overwriting the only backup.
- Store backups in a dedicated application data directory.
- Allow manual backup.
- Allow backup to USB/external folder.

Example:

Backups/
    backup-2026-10-01.db
    backup-2026-10-02.db
    backup-2026-10-03.db

The exact retention count may be configurable.

---

46. Restore

Never destroy the current database without creating a recovery point.

48. Database Safety

SQLite must use transactions for operations that modify multiple related records.

Example sale transaction:

Create Invoice
+
Create Invoice Items
+
Reduce Inventory
+
Record Payment
+
Record Cost
+
Commit

Either all operations succeed or none of them should be committed.

The system must prevent partially saved sales.

- Avoid exposing Node.js APIs to the renderer.
- Validate monetary values.
- Validate quantities and weights.
- Prevent negative or impossible values unless explicitly allowed.
- Handle database errors safely.

# PRD ADDENDUM — decisions resolved during hardening (applies on top of PRD §1–84)

Each item cites the PRD text it is derived from. Items marked **NEEDS OWNER APPROVAL** are implemented in the most conservative reading and are listed again in RELEASE_READINESS.md.

## 85. LBP rounding (clarifies §17, §25–27)
Four different numbers are kept apart everywhere (service, payment dialog, receipt, reports):
1. **Amount owed (exact)** – invoice total as stored; never rounded. Reports use only this.
2. **Cash due in LBP** – shown only for LBP-only tenders: the exact LBP-equivalent rounded **up** to the next 5,000 (87,300 → 90,000, the §17 example). Payments that include any USD are compared **exactly**, so no customer is overcharged by a rounding they did not choose.
3. **Amount received** – what the customer handed over, stored as entered (USD cents + LBP).
4. **Change** – USD change is floored to whole cents; LBP change is rounded up to the next 5,000 (**NEEDS OWNER APPROVAL**: favours the customer; the PRD only specifies the 87,300 → 90,000 example).
Debt/credit is always measured against the exact amount owed. Rounding is never applied to stored totals, cost, profit or reports.

## 86. Selling beyond recorded stock (§29, §64) — rule D3
A sale can **never** take stock below zero. The POS warns before it happens (product dialog shows available/requested including what is already in the cart; "Complete Sale" is disabled while the cart exceeds stock) and the server refuses it atomically. The owner fixes the stock first (Add Stock / Adjust). Rationale: simplest consistent rule, keeps stock movements and cost reports trustworthy.

## 87. Waste and profit (§36, §32, §50) — rule D5
Waste records quantity, reason (Expired/Damaged/Spoiled/Other) and a **cost snapshot at the time of waste** (USD cents). Net profit = gross profit − expenses − waste cost. Waste is not part of COGS, so it is deducted exactly once. Later cost or rate changes never alter historical waste. Waste on a product with no recorded cost counts as $0.00 and is flagged "cost not recorded".

## 88. Resolved without new business rules
- **D2 costing** – latest purchase cost snapshotted per sale; no FIFO/LIFO (§31, §33 forbid advanced costing; §31 forbids overwriting historical cost).
- **D7 menu language** – the native menu exists only in development builds; the packaged app has none, and all UI text is localized (§8).

## 89. Draft cart recovery (new, supports §23, §69, §77)
An unfinished cart is saved locally (product ids, quantities, weight final price only – no prices, customer or payment data). After an unexpected restart the cashier is offered **Restore / Discard**; a draft is clearly labelled "not an invoice". Restoring re-prices from the current price list and uses the exchange rate current at completion. Each draft carries the sale's idempotency key, so a draft whose sale already committed is discarded and a draft can never be sold twice. Items that are no longer sellable are dropped and reported.

## 90. Still open — NEEDS OWNER APPROVAL
- D4: returned goods are restocked (§37 "inventory updated appropriately"); damaged returns must be recorded as waste afterwards.
- D6 / §85.4: LBP change rounded up.
- Report category names are not snapshotted per sale.
