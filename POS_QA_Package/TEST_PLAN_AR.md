# خطة الاختبار الشاملة — Local POS

## 1) حدود الحزمة
هذه الحزمة مبنية على مصدر المشروع المتاح في جلسة العمل، ومخطط SQLite ذي `schema_version` حتى 3. تحتوي على:
- `pos_app_empty.sqlite`: قاعدة نظيفة بمخطط مهيأ، بلا بيانات تشغيل أو إعدادات متجر، مع الاحتفاظ بسجل إصدارات المخطط كي لا تعاد تهيئة الجداول.
- `pos_app_test_data.sqlite`: قاعدة بيانات اصطناعية للاختبار، تتضمن سجلات بيع ومخزون وعملاء ومرتجعات ومصروفات وصور SVG توضيحية.
- `product_images/`: الصور المستخرجة من بيانات المنتجات التجريبية.

**هذه ليست نسخة احتياطية من بيانات متجرك الحقيقية.** النسخة الاحتياطية الحقيقية يجب إنشاؤها من داخل التطبيق أو بأداة SQLite آمنة من قاعدة التشغيل الفعلية. لا تستبدل `local-pos.db` بقاعدة الاختبار أو الفارغة قبل نسخ احتياطية منفصلة.

## 2) تجهيز بيئة اختبار آمنة
1. أغلق التطبيق بالكامل.
2. أنشئ نسخة احتياطية من قاعدة بياناتك الحقيقية من شاشة النسخ الاحتياطي داخل التطبيق، واحفظ نسخة ثانية خارج الكمبيوتر (USB/قرص خارجي).
3. لاختبار الواجهة، الأفضل استخدام نسخة منفصلة من التطبيق/Windows user profile أو نسخة تجريبية من مجلد بيانات التطبيق. لا تجرّب الاستعادة على قاعدة المتجر الحقيقية.
4. قاعدة التشغيل في Windows وفق الكود: `%APPDATA%/Local POS/local-pos.db` (قد يختلف اسم مجلد المستخدم حسب اسم التطبيق الفعلي). لا تحذف هذا الملف لتجربة القاعدة الفارغة إلا بعد حفظ نسخة مؤكدة منه.
5. انسخ القاعدة المطلوبة إلى مجلد بيانات اختبار منفصل، ثم وجّه نسخة الاختبار إليها فقط. المشروع الحالي يحدد المسار الافتراضي داخل `app.getPath('userData')`، لذلك مجرد وضع ملف بجانب ملف EXE لا يغيّر قاعدة التطبيق تلقائياً.

## 3) ترتيب التشغيل المقترح
### المرحلة A — فحوصات المصدر الآلية
من مجلد المشروع:
```bash
npm ci
npm test
npm run build
```
على Windows، نفّذ أيضاً:
```powershell
npm run package:win
```
إذا فشل `npm ci` أو إعادة بناء `better-sqlite3`، احفظ كامل المخرجات ولا تتجاوز الفشل. لا تعتبر بناء Linux دليلاً على نجاح Windows installer.

### المرحلة B — فحص قواعد البيانات
باستخدام SQLite CLI إن كان مثبتاً:
```sql
PRAGMA integrity_check;
PRAGMA foreign_key_check;
```
نفّذ الأمرين على القاعدتين. المتوقع: `integrity_check` يرجع `ok` و`foreign_key_check` لا يرجع صفوفاً.
- الفارغة: يجب ألا تحتوي بيانات متجر/منتجات/فواتير/عملاء/مخزون؛ جدول `schema_version` يبقى موجوداً.
- التجريبية: افحص بياناتها ثم افتحها فقط في بيئة اختبار.

### المرحلة C — الاختبار الوظيفي من الواجهة
استخدم `TEST_CHECKLIST_AR.md` بالترتيب. سجّل لكل حالة: PASS / FAIL / BLOCKED / NOT TESTED، مع رقم الحالة وصورة شاشة أو فيديو قصير عند الفشل.

### المرحلة D — النسخ والاستعادة
1. داخل نسخة الاختبار أضف منتجاً وفاتورة تجريبية.
2. أنشئ نسخة احتياطية من شاشة التطبيق إلى مجلد محلي، ثم نسخة إلى USB.
3. تحقق من وجود الملف وحجمه غير الصفري.
4. أغلق التطبيق، انسخ ملف النسخة إلى مجلد آخر، وافحصه بـ `PRAGMA integrity_check` و`foreign_key_check`.
5. جرّب الاستعادة داخل نسخة الاختبار فقط. تحقق من رجوع المنتج والفاتورة، ثم أعد تجربة قاعدة اختبار نظيفة.
6. اختبر USB مفصولاً/مساحة غير كافية/ملف نسخة تالف فقط في بيئة الاختبار، وتأكد من ظهور خطأ مفهوم وعدم تلف القاعدة الأصلية.

### المرحلة E — اختبار Windows الواقعي
على جهاز Windows المستهدف: تثبيت نظيف، تشغيل أول مرة، إعداد المتجر، إغلاق وفتح، إعادة تشغيل الجهاز، تحديث فوق نسخة سابقة، اختصار سطح المكتب، الطباعة إن كانت مطلوبة، والنسخ/الاستعادة. لا يمكن تأكيد هذه النقاط من فحص ملفات المصدر وحده.

## 4) قاعدة بيانات الاختبار — بيانات اصطناعية
تحتوي القاعدة على سجلات تجريبية (لا تستخدم أسماء أو أرقام اتصال حقيقية)، منها:
- 8 فئات، 12 منتجاً، 12 سجل مخزون، 18 حركة مخزون.
- 5 عملاء، 5 فواتير، 6 بنود فواتير، 5 دفعات.
- مرتجع واحد وبند مرتجع، 3 مصروفات، 5 حركات حساب عميل، وسجلّي تدقيق.
- سعر صرف محفوظ: 89,500 ل.ل لكل دولار.
- 12 صورة SVG توضيحية مضمنة في المنتجات ومصدّرة أيضاً إلى `product_images/`.

هذه البيانات تغطي عينات مفيدة لكنها **لا تعني أن جميع الحالات قد اختُبرت**. الحالات السلبية والحدّية موضحة في قائمة الاختبار.

## 5) قواعد قبول الاختبار
- PASS فقط عند تنفيذ الخطوات ومشاهدة النتيجة المتوقعة فعلياً.
- FAIL عند اختلاف النتيجة، أو فساد بيانات، أو توقف التطبيق، أو ظهور حساب خاطئ.
- BLOCKED إذا تعذر تنفيذ الاختبار بسبب البيئة أو نقص جهاز/طابعة/USB.
- NOT TESTED إذا لم ينفذ بعد.
- لا تستخدم عبارة «خالي من الأخطاء» أو «آمن 100%». الإصدار يصبح مرشحاً للتسليم عندما تنجح الوظائف الحرجة، وتنجح الاستعادة، ولا توجد إخفاقات حرجة مفتوحة، وتُوثق القيود المعروفة.

## 6) ما ترسله لي بعد كل جولة
أرسل:
1. `TEST_RESULTS_TEMPLATE.md` بعد تعبئة الحالات التي نفذتها.
2. نص مخرجات `npm ci`, `npm test`, `npm run build`، و`npm run package:win` إن نفذته.
3. صور/فيديو للحالات الفاشلة فقط مع رقم الحالة.
4. نتيجة `PRAGMA integrity_check` و`PRAGMA foreign_key_check` قبل وبعد الاستعادة.
5. لا ترسل قاعدة بيانات المتجر الحقيقية أو أرقام هواتف/أسماء زبائن حقيقية أو كلمات مرور/مفاتيح. استخدم القاعدة الاصطناعية.

## 7) ملاحظات مهمة من مراجعة الكود المتاح
- مسار قاعدة التشغيل يدار عبر Electron `app.getPath('userData')`، لذلك تبديل ملف القاعدة يتطلب إعداد بيئة اختبار منفصلة، وليس مجرد فتح ملف SQLite من الواجهة.
- خدمة الاستعادة تنشئ نسخة ما قبل الاستعادة ثم تنسخ الملف المحدد إلى قاعدة التشغيل؛ يجب اختبارها على نسخة اختبار فقط.
- خدمة النسخ تستخدم SQLite `VACUUM INTO` لإنتاج لقطة متسقة.
- فحوصات الواجهة والطابعة وWindows installer وفشل القرص/انقطاع الكهرباء لا يمكن الجزم بها دون تنفيذها على البيئة المستهدفة.
